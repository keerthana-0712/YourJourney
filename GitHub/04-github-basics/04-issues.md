# Issues

An **Issue** is a tool used on GitHub to track:

* bugs
* feature requests
* improvements
* tasks
* discussions

In simple words:

> An Issue is a task, problem, or suggestion related to a project.

Issues help developers stay organized and collaborate effectively.

---

# Why Issues Are Important

Imagine a project with thousands of users.

Users may discover:

* bugs
* missing features
* performance problems
* documentation mistakes

Instead of sending messages everywhere, GitHub provides a central place called:

```txt
Issues
```

This helps project maintainers manage everything properly.

---

# Real-World Example

Imagine a college group project.

Someone notices:

```txt
Login page is not working.
```

Instead of just telling a friend verbally, they create an issue:

```txt
Title:
Login button not responding

Description:
When I click the login button, nothing happens.
```

Now the entire team can see and track the problem.

# Anatomy of an Issue

A good issue usually contains:

## Title

Short description.

Example:

```txt
Fix navbar alignment issue
```

---

## Description

Detailed explanation.

Example:

```txt
Navbar links overlap on small screens.
```

---

## Steps to Reproduce

Explain how to see the problem.

Example:

```txt
1. Open homepage
2. Resize browser window
3. Observe navbar overlap
```

---

## Expected Result

Explain what should happen.

Example:

```txt
Navbar should stay aligned properly.
```

# Issue Labels

Many repositories use labels.

Examples:

| Label            | Purpose                    |
| ---------------- | -------------------------- |
| bug              | Something is broken        |
| enhancement      | New feature or improvement |
| documentation    | Documentation work         |
| help wanted      | Contributors needed        |
| good first issue | Beginner-friendly task     |

---

# What is a "Good First Issue"?

Many open-source projects create:

```txt
good first issue
```

labels.

These are tasks specifically designed for beginners.

Examples:

* fixing spelling mistakes
* improving README files
* updating documentation
* small bug fixes

This is often the best way to start contributing to open source.

---

# Issues vs Pull Requests

Many beginners confuse these concepts.

| Issues                 | Pull Requests   |
| ---------------------- | --------------- |
| Report problem or task | Submit solution |
| Discussion             | Code changes    |
| Identify work          | Complete work   |

Simple understanding:

```txt
Issue = Problem

Pull Request = Solution
```

---

# Common Beginner Mistakes

## Creating Vague Issues

Bad example:

```txt
Website broken
```

Good example:

```txt
Login page shows blank screen after clicking submit
```

Always be specific.

---

## Not Checking Existing Issues

Before creating a new issue:

Check if someone has already reported it.

Duplicate issues create confusion.

---

## Writing Too Little Information

Provide:

* clear explanation
* screenshots (if possible)
* reproduction steps

This helps maintainers understand the problem quickly.

# Real Open Source Workflow

```txt
User Finds Problem
        ↓
Creates Issue
        ↓
Contributor Works on Fix
        ↓
Creates Pull Request
        ↓
Maintainer Reviews
        ↓
Issue Gets Closed
```

This workflow is used by thousands of open-source projects.
